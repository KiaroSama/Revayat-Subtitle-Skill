## 2. F01 — Long supported text still breaks the lint pipeline

### Reproduction and impact

On the baseline release binary, a UTF-8 file containing 200,000 ASCII `x` characters followed by a newline and `خوب ترین...` is only 200,019 bytes. `revayat-subtitle lint --check --json` reports the expected mechanics changes with exit `1`. Adding `--style` instead exits `2`, produces no JSON result, and reports `Max limit for backtracking count exceeded`. Long Persian text and repeated candidate words expose the same failure family.

A second independent control, `یک ` followed by 1,000,000 ASCII `x` characters and ` است`, triggers `Max stack size exceeded for backtracking` inside a genuinely matching style expression. A Unicode seek-filter prototype fixes the first example but fails this second one. Therefore, merely raising the backtracking limit, enabling a seek optimization, splitting on lines, suppressing an error, or dropping a rule is not complete remediation.

### Root cause and repair contract

The locked `fancy-regex 0.20.2` default seek-usefulness heuristic recognizes ASCII letters/digits and regex punctuation, so some derived Persian-only alternative expressions do not receive the expected prefilter. Independently, an unbounded non-whitespace body followed by optional characters and boundaries can exhaust the VM stack. The optional style matcher must not rely on that VM for its fixed regular rule bodies.

The final real-CLI control also exposed the required normalization prepass: even after style matching succeeds, `(?<=[۰-۹])%` can exhaust the VM while scanning a million-character line without an eligible percent sign. Its derived `%` prefilter is also rejected by that heuristic. A finite pass over every normalization rewrite on long Latin, Persian, enclitic, bang, and percent cases isolated this rule as the remaining failure. The repair replaces it with regular `([۰-۹])%` and restores the captured digit using `${1}٪`. A digit cannot be another match's trailing percent, so consuming it preserves adjacent conversions and exact replacement counts. This closes the composed CLI path, including style-disabled normalization, without changing limits or adding a global experimental filter.

The new `persian_lint/style.rs` uses the existing `regex` dependency for style-body matching. Empty named captures retain each original boundary position, which is checked against the exact Python-compatible word-character predicate: Unicode general categories `L` and `N`, plus underscore; combining marks and joiners are not word characters. The fixed alternatives have distinct literal bodies, preserving their original preference under this validation. The implementation retains the extra whitespace controls U+001C–U+001F, multiline whitespace, rule and alternative ordering, original notes, protected-region masking, and character-based context. A rejected candidate restarts at the next Unicode scalar so it cannot hide a later overlapping valid candidate. The `نقش (مهم|کلیدی|حیاتی)` alternative intentionally has no right word boundary. Existing normalization output and statistics are preserved.

### Required acceptance

- Both independent long-input reproductions must succeed through the public style API; the public CLI must retain its documented JSON and exit-status behavior.
- Exercise long noise followed by a real style match, a long matching body, dense rejected-boundary prefixes, supported input-size limits, and both style-enabled and style-disabled operation.
- Compare all 13 style rules against the prior matcher on ordinary accepted inputs, including Latin/Persian letters, all number categories, underscore, combining marks, joiners, newlines, whitespace controls, and overlapping candidates. Preserve protected code/URLs and exact context text.
- Keep the meaningful long-input regressions in ordinary workspace CI. Do not declare this finding closed on the shorter example alone.

`persian_lint_style_bounds.rs` adds eight style regressions, including an exact 16 MiB logical line and 100,000 rejected candidates before a real match, plus a normalization regression for long Latin/Persian/percent input, adjacent and repeated percent signs, exact statistics, and protected code/URLs. `lint_scanner_bounds.rs` exercises the actual CLI with the original example, million-character matching body, exact 16 MiB limit, JSON/exit semantics, and fixed text through stdout. Both new prepass tests were red before the percent repair. The final differential counts and release-binary receipt are recorded with the repair PR. This is a mechanics/style-suggestion repair, not a certification of translation quality.

## 3. F02 — Duplicate out-of-media ASS rows change FPS and visible timing

### Reproduction and impact

An authored native `VadResult` describes 45,000 ms of audio, ordinary visible speech cues, and an ASS event at 50,000–51,000 ms. Adding 99 identical copies of that tail event leaves the complete 100-second subtitle activity raster byte-for-byte identical. Nevertheless, baseline synchronization selects `25 / 23.976 = 1.0427093760427095` for the single-tail document and `1.0` for the duplicate-tail document, changing the earlier visible cue timestamps. Global offset, split offset, and snap limits are all zero. Both native output and the exact report replay reproduce the difference. The bounded search stopped at its first counterexample after 20 comparisons.

### Implemented repair

`build_subtitle_activity` represents overlaps with the maximum activity in each frame. The old tail-energy helper instead adds each cue's squared fractional/full-frame energy independently. Duplicate or overlapping ASS rows therefore inflate the denominator of the FPS score beyond the bounded FFT window.

`align_energy.rs` computes energy from the same per-frame maximum as the existing rasterizer. Each tail cue contributes at most two fractional edge intervals and one full-frame interval. Ordered weighted events maintain the largest active coverage and integrate its squared `f32` raster value over each frame range. The structure scales with cue/event count, not the duration or distance of a tail. Collection and event scanning both honor cancellation, without an uninterruptible global sort.

`align.rs` uses this helper while retaining the full-energy penalty, the unity candidate's `+0.02` preference, existing lag bounds, per-cue refinement, ASS ordering/grouping, SRT repairs, and exact report replay. Do not remove the full-energy penalty to make this example pass; the feature-length noisy-unity regression still protects its original purpose.

### Required acceptance

- `duplicated_ass_tail_does_not_change_fps_or_visible_cue_timing` requires equal complete activity, the expected non-unity FPS, equal selected FPS/global shift, and identical earlier visible cue times.
- The dense-raster oracle covers 240 combinations of empty, duplicate, nested, overlapping, adjacent, fractional, invalid/empty, and window-straddling intervals, with several frame sizes and tail boundaries. The oracle uses the unchanged rasterizer, not a copy of the sparse implementation.
- A 24-hour tail must complete with a bounded number of checkpoints and without a timeline-sized tail allocation. Cancellation must propagate during collection and sweep; a zero frame size retains its existing convention.
- Preserve both FPS drift directions, noisy feature-length unity, per-dialogue refinements, zero-offset limits, reversed ASS event order, overlapping rows, SRT repair, and native/external-worker replay controls.
